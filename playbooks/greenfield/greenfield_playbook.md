# Greenfield Playbook Specification

This document defines the orchestrator specification for the **Greenfield Playbook**. The Greenfield Playbook is the "happy path" master state machine that guides a project from a completely empty directory to a fully qualified production release.

---

## 1. How the Playbook Handles Actions (Orchestration)

The playbook is an **Orchestrator**, not an executor. It does not write code or draw architectural diagrams itself. Instead, it handles actions by:

1. **State Parsing**: It constantly reads `agent-workspace/plans/<scope>/PROCESS_STATUS.md` to determine the current macro-state of the project.
2. **Action Invocation**: Based on the state, the playbook triggers the appropriate action command (e.g., triggering `/plan` once `/init` is `[x] Done`).
3. **Context Passing**: It ensures that the output state of one action (e.g., the `phase-5-test.md` artifact generated by `/plan`) is correctly recognized as the required input for the next action (`/implement`).
4. **Handoff Verification Gate**: Before transitioning between actions, the playbook executes the deterministic handoff verifier (`verify-action-handoff.sh`). If the preceding action has not reached `[x] Done` (or `[-] Not In Scope`) on disk, the playbook halts fail-closed, refusing to start the next action.

---

## 2. Automation Boundaries & Execution Modes

The playbook clearly separates what requires human intervention from what can run autonomously.

### Manual Orchestration (Default Mode: `/greenfield`)
By default, the playbook operates in a **Hold-and-Confirm** loop between major actions.
- The playbook executes an action (e.g., `/plan`).
- Once `/plan` completes, the playbook halts, displays a summary of the action's output, and asks the user: *"Are you ready to begin `/implement` based on these blueprints?"*

### Fully Automated Orchestration (`/greenfield --auto`)
If the user trusts the agent and the requirements are extremely clear, the playbook can automatically execute action commands using their internal automation flags:
- It triggers `/init --auto`
- It reads the exit code. If `0`, it triggers `/plan --auto`.
- It reads the exit code. If `0`, it triggers `/implement --auto`.
- **Hard Stop Exception**: Even in `--auto` mode, the **Structural Gate (Law II: WHAT)** inside `/implement` cannot be bypassed. The playbook will always pause to show the user the `mkdir` tree proposal before writing to disk.

## 3. Playbook Steps (The Greenfield Sequence)

The Greenfield playbook bypasses legacy ingestion and proceeds through the purest sequence of the Guards Framework:

*   **Step 1: Orchestrate `/init`**
    *   **Goal**: Establish the Control Plane and `PROCESS_STATUS.md`.
    *   **Playbook Role**: Sets the target Git origin, initializes the repository, and creates the `.agents/` guard structures.
    *   **Handoff Checkpoint**:
        ```bash
        ./global/antigravity/guards/scripts/verify-action-handoff.sh --completed-action init --next-action plan
        ```
*   **Step 2: Skip `/process`**
    *   **Goal**: Because this is a new project, there is no legacy code.
    *   **Playbook Role**: Explicitly marks `/process` as `[-] Not In Scope` in `PROCESS_STATUS.md`.
*   **Step 3: Orchestrate `/plan`**
    *   **Goal**: Author the 6-phase blueprints (`phase-1-summary.md` to `phase-6-operation.md`).
    *   **Playbook Role**: Invokes `/plan`, ensuring the agent completes the micro-architecture grill engine (Q1-Q9).
    *   **Handoff Checkpoint**:
        ```bash
        ./global/antigravity/guards/scripts/verify-action-handoff.sh --completed-action plan --next-action implement
        ```
*   **Step 4: Orchestrate `/implement`**
    *   **Goal**: Provision repositories and scaffold code/tests.
    *   **Playbook Role**: Triggers the 3-leg dual grounding check, executing `--tests-only` red-first harness construction if selected, followed by feature scaffolding.
    *   **Handoff Checkpoint**:
        ```bash
        ./global/antigravity/guards/scripts/verify-action-handoff.sh --completed-action implement --next-action qualify
        ```
*   **Step 5: Orchestrate `/qualify`**
    *   **Goal**: Execute tests and lock the release.
    *   **Playbook Role**: Runs the test harness in `codebase-qualify/`, generating the `QUALIFICATION_REPORT.md`.
    *   **Handoff Checkpoint**:
        ```bash
        ./global/antigravity/guards/scripts/verify-action-handoff.sh --completed-action qualify --next-action operate
        ```
*   **Step 6: Orchestrate `/operate`**
    *   **Goal**: Finalize CI/CD and deploy.
    *   **Playbook Role**: Invokes Docker builds and promotion scripts in `codebase-devops/`.

## 4. User Observability (Following the Process)

To ensure the user is never lost during a massive full-lifecycle generation, the playbook utilizes the **Workflow Context Notification Law** (from `process_handling.md`) at three distinct layers:

1. **Persistent State Matrix (`PROCESS_STATUS.md`)**: The user can open this file at any time. The playbook guarantees that the top block (the Workflow Matrix) and bottom block (Daily History Log) are perfectly up-to-date with the macro progress.
2. **The Audit Log (`GRILL_STATUS.md`)**: Every Q&A session, decision, constraint, or God-Mode override handled by the playbook is appended here, providing a historical transcript of *why* the playbook did what it did.
3. **Turn-by-Turn UI Banners**: Before every major message, the playbook forces the agent to output a contextual header so the user knows exactly where they are in the lifecycle:
   ```markdown
   > 📍 **Active Playbook**: /greenfield | **Active Action**: /implement | **Node**: S4 (Scaffolding)
   ```
